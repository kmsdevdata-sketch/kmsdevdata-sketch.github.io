08 · Troubleshooting

명령의 성공과 사용자가 접속할 수 있는 상태를 따로 추적했습니다

배포 명령이 정상 종료돼도 컨테이너, 공개 URL과 DNS가 모두 준비됐다고 볼 수 없었습니다. 실패가 발생한 단계를 구분하고, 후보 환경을 운영 환경으로 확정하기 전까지 기존 서비스를 유지했습니다.

ECS 배포는 끝났지만 새 컨테이너가 응답하지 않음

재현과 추적

Terraform과 ECS 명령은 성공했지만 공개 URL은 응답하지 않았습니다. ECS Service 전체 상태가 아니라 이번 배포가 생성한 Task Definition과 새 Task의 rollout을 따로 추적했습니다.

원인

인프라 변경 명령의 완료와 새 컨테이너가 요청을 받을 준비가 된 시점 사이에 차이가 있었습니다. 기존 Task의 정상 상태가 새 배포의 성공처럼 보일 수도 있었습니다.

수정과 확인

새 Task의 실행 상태와 후보 URL의 연속 응답을 모두 통과해야 다음 단계로 이동하도록 바꿨습니다. 후보가 실패하면 origin을 전환하지 않아 기존 서비스가 계속 요청을 처리했습니다.

컨테이너는 정상이지만 고정 URL 전환이 실패함

재현과 추적

후보 컨테이너의 직접 주소는 정상이었지만 사용자가 접속하는 고정 URL은 이전 환경을 가리키거나 응답하지 않았습니다. 후보 검증, origin 변경, 공개 URL 검증을 별도 단계로 기록했습니다.

원인

컨테이너 상태와 Cloudflare origin 상태를 하나의 성공 조건으로 묶어, 전환 이후의 실패를 구분할 수 없었습니다.

수정과 확인

후보 URL을 먼저 검증한 뒤 origin을 변경하고, 고정 URL을 다시 확인했습니다. 마지막 검증이 실패하면 이전 origin으로 되돌리고 복구 결과까지 작업 상태에 남겼습니다.

같은 프로젝트의 동시 요청이 배포 상태를 덮어씀

재현과 추적

같은 프로젝트에 요청 두 건을 동시에 보내면 각각 컨테이너와 공개 URL을 변경할 수 있었습니다. 요청 ID가 달라도 배포 대상 프로젝트는 같다는 점을 잠금 기준에 반영해야 했습니다.

원인

작업 큐가 요청 실행 순서는 관리했지만 프로젝트별 활성 배포를 하나로 제한하지 않았습니다.

수정과 확인

PostgreSQL transaction과 unique constraint로 프로젝트별 잠금을 만들었습니다. 한 요청만 잠금을 얻고 나머지는 409로 종료했으며, 실패와 재시작 뒤 잠금이 남지 않는지도 함께 확인했습니다.
