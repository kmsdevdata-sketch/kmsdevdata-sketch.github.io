주문 흐름의 상태 오류를 추적했습니다

사용자 시나리오를 연결하는 과정에서 단일 기능 테스트만으로 드러나지 않던 오류가 발생했습니다. 재현 조건과 상태 변경 순서를 따라가며 원인을 좁히고 회귀 시나리오를 추가했습니다.

01. 주문 CTA가 새로고침 전까지 나타나지 않던 문제

재현과 추적

일반 채팅은 즉시 표시됐지만 주문서 제출, 주문확인서와 결제 완료 CTA는 새로고침 뒤에 나타났습니다. 이벤트 발행 로그와 Topic 구독 경로를 비교해 CTA 이벤트가 문의 목록 Topic에만 전달되는 경우를 확인했습니다.

원인

채팅방 타임라인과 문의 목록 갱신이 서로 다른 코드 경로에 있었고, 일부 이벤트는 트랜잭션 커밋 전에 발행됐습니다. 이벤트 직후 재조회하면 아직 저장되지 않은 데이터를 읽을 가능성도 있었습니다.

수정과 확인

타임라인 이벤트를 공통 발행 흐름으로 통합하고 채팅방 Topic과 사용자별 문의 Topic의 책임을 나눴습니다. AFTER_COMMIT 이후 Redis Pub/Sub으로 전달해 주문서 제출부터 결제 완료까지 새로고침 없이 갱신되는지 확인했습니다.

02. 과거 주문이 현재 상담 상태를 변경하던 문제

재현과 추적

한 상담방에서 두 번째 주문서를 제출한 뒤 첫 번째 주문의 결제나 픽업을 처리하면 현재 상담 상태가 함께 변경됐습니다. 주문 이벤트가 어떤 submission에서 시작됐는지 역으로 추적했습니다.

원인

Inquiry의 WAITING·IN_PROGRESS 상태가 현재 상담 진행 여부와 개별 주문서 확인 여부, 주문 주기를 모두 나타내고 있어 과거 이벤트와 현재 작업을 구분할 기준이 없었습니다.

수정과 확인

주문서별 sellerViewedAt과 currentOrderFormSubmissionId를 추가해 책임을 분리했습니다. 과거 주문은 정상 처리하면서 현재 submission과 연결된 이벤트만 상담 상태를 변경하도록 회귀 시나리오를 구성했습니다.

03. 현재 이미지가 과거 주문 기록까지 바꾸던 문제

재현과 추적

구매자가 상담방의 시작 이미지를 변경하면 이미 제출한 주문서 CTA와 주문 상세 화면에서도 새 이미지가 나타났습니다. 화면별 이미지 조회 경로를 비교했습니다.

원인

과거 주문 화면도 변경 가능한 Inquiry.startReferenceAsset을 참조하고 있어 주문 당시 값이 보존되지 않았습니다.

수정과 확인

제출 시점의 참조 이미지를 OrderFormSubmission에 스냅샷으로 저장했습니다. 주문 CTA와 상세·목록이 해당 submission의 이미지를 조회하도록 변경해 이후 상담 이미지가 바뀌어도 주문 기록을 유지했습니다.
