07 · Technical Decisions

업무 흐름이 끊기지 않도록 상태와 이벤트의 기준을 나눴습니다

실시간 상담, 반복 주문과 외부 결제는 서로 다른 실패 조건을 가집니다. 하나의 상태나 처리 시점으로 묶지 않고, 각 흐름에서 확정해야 할 기준을 따로 설계했습니다.

01. 트랜잭션과 실시간 타임라인의 일관성

문제

주문서와 결제 안내 이벤트를 저장 직후 발행하면 클라이언트의 재조회가 데이터베이스 커밋보다 먼저 실행될 수 있었습니다. 트랜잭션이 롤백돼도 이미 전송한 이벤트는 되돌릴 수 없었습니다.

검토

단일 인스턴스에서 즉시 발행하는 방식은 화면 반응은 빠르지만 데이터 확정 여부와 다중 ECS 인스턴스의 WebSocket 연결을 함께 보장하지 못했습니다.

선택과 결과

타임라인은 트랜잭션 안에서 저장하고 이벤트는 AFTER_COMMIT에 발행했습니다. Redis Pub/Sub이 각 ECS 인스턴스로 이벤트를 전달해, 사용자는 확정된 주문 상태를 새로고침 없이 확인할 수 있게 했습니다.

02. 반복 주문의 현재 상태와 과거 기록 분리

문제

한 상담방에서 주문이 반복되기 때문에 문의방 상태 하나로 상담 진행, 주문서 확인과 주문 주기를 함께 판단하면 과거 주문 이벤트가 현재 상담을 바꿀 수 있었습니다.

검토

문의방은 현재 처리할 상담이 있는지만 나타내고, 판매자가 실제로 확인한 주문서와 현재 진행 중인 주문 주기는 별도로 식별해야 했습니다.

선택과 결과

문의방 상태, 주문서별 sellerViewedAt과 currentOrderFormSubmissionId의 책임을 분리했습니다. 과거 주문의 결제와 픽업은 처리하되 현재 주문 주기와 일치할 때만 상담 상태를 변경했습니다.

03. 외부 결제 요청의 멱등성과 상태 추적

문제

새로고침, 중복 클릭과 네트워크 재시도로 같은 주문확인서에 결제 요청이 반복될 수 있었습니다. 외부 요청의 결과가 늦게 도착할 가능성도 함께 고려해야 했습니다.

검토

결제 요청과 주문 생성을 한 상태로 관리하면 외부 응답을 기다리는 과정과 실제 주문 완료 상태를 구분하기 어려웠습니다.

선택과 결과

PaymentAttempt를 주문과 분리해 진행 중인 시도를 재사용했습니다. 승인 결과를 반영할 때 기존 주문과 결제 상태를 먼저 확인해 같은 주문이 중복 생성되지 않도록 구성했습니다.
